# bluechip repository guide

bluechip is a pnpm workspace written in TypeScript 7 with Effect v4, laid out like the Effect
repository. Read this file before changing anything, then load the skills under [Skills](#skills)
that match the task.

## Workspace map

- `packages/*`: publishable packages, each with its own public boundary.
  - `packages/domain` (`@bluechip/domain`, private): shared ids, errors, live events and the HTTP API contract
    (`BluechipApi`, Effect `HttpApi`); the server implements it, the web app calls it. Depends only on `effect`.
  - `packages/chain` (`@bluechip/chain`, private): Base from Effect: `ChainClient` (viem), contract addresses (USDC,
    EntryPoint, every Coinbase stock with a Chainlink feed), ABIs, and `DevChain` cheatcodes for the local fork.
  - `packages/devnet` (`@bluechip/devnet`, private): a local Base for tests, Anvil and Alto per Vitest worker,
    started from a state captured once from a fork (`state/devnet.state.gz`, rebuilt by `pnpm devnet:capture`), with
    every contract bluechip uses at its real address and settable price feeds (`Devnet`, `DevnetTest`).
  - `packages/ui` (`@bluechip/ui`, private): the design system: Tailwind v4 theme, base components on Base UI,
    bluechip's product components, motion and illustrations. Presentational only.
- `apps/*`: runnable applications (private).
  - `apps/web` (`@bluechip/web`): the TanStack Start web app.
  - `apps/uikit` (`@bluechip/uikit`): a TanStack Router single-page app showing every `@bluechip/ui` component
    (`pnpm --filter @bluechip/uikit dev`, port 4000).
  - `apps/server` (`@bluechip/server`): the Effect v4 HTTP server; Postgres through Drizzle ORM (1.0 RC, Effect
    driver), SQL migrations in `apps/server/drizzle/` generated by `drizzle-kit` (never edited by hand).
- `contracts/`: bluechip's onchain policies in Solidity (Foundry, Soldeer dependencies): `AerodromeTradePolicy`
  (validation), `TradeGuard` (execution: measures what moved, values the portfolio, then runs the session's rule
  contracts, `src/rules/*Rule.sol`), Namera v2 policies deployed by CREATE2 at the same address everywhere.
  `contracts build` writes their addresses and ABIs to `packages/chain/src/policies/Deployed.ts`. `test/vectors.json`
  is a frozen fixture of the rules' behaviour. A change to their bytecode moves their addresses: rebuild, then
  `pnpm devnet:capture`, and update the gas snapshot (`node scripts/bin.ts contracts snapshot`).
- `scripts/`: the repository's tooling, one Effect CLI (`node scripts/bin.ts <command>`).
- `scratchpad/`: ad hoc probes: `scratchpad/<name>.ts`, run with `node`, deleted afterwards (git
  ignores everything there but its skeleton).

Dependencies point inward: apps depend on packages, packages never depend on apps.

## Commands

| Command                | What it does                                                        |
| ---------------------- | ------------------------------------------------------------------- |
| `pnpm check`           | Everything CI runs, in order. Run it before every push.             |
| `pnpm typecheck`       | Type-check everything with tsrs (TypeScript 7 + Effect diagnostics) |
| `pnpm lint`            | oxlint with Effect's rules (`lint:fix` applies fixes)               |
| `pnpm format`          | Format with dprint (`format:check` only checks)                     |
| `pnpm test`            | Run every Vitest project once (`test:watch` for watch mode)         |
| `pnpm test:fork`       | Deploy the policies to a running fork, then check real-Base facts   |
| `pnpm contracts:test`  | Format check, lints and Foundry tests of `contracts/`               |
| `pnpm contracts:build` | Build `contracts/` and regenerate `Deployed.ts`                     |
| `pnpm build`           | `tsc -b`, then each package's build                                 |
| `pnpm circular`        | Fail on import cycles between modules                               |

Local services: copy each `.env.example` to `.env.local` (root: Docker Compose's fork RPC; `apps/server`, with
`AGENT_KEY_ENCRYPTION_KEY` from `openssl rand -base64 32`; `apps/web`; never committed), then `pnpm dev`: Postgres, the local chain (the devnet on Anvil, 8545, no RPC; its
feeds and pools follow the server's market prices every 15 s, and its state carries over between runs in
`.data/devnet/`), the Alto bundler (4337), migrations, then the server (8080), the web app (3000), the component
kit (4000) and the Trigger.dev job runner, in one terminal. Ctrl+C stops everything; `pnpm dev:stop` stops anything
left running (`--all` stops Postgres too). `pnpm dev --fork` uses an Anvil fork of Base through your RPC instead,
`--reset-chain` starts the local chain again from the capture, and `--no-chain` (or `--no-uikit`, `--no-jobs`) skips
parts. Fork money: `pnpm --filter @bluechip/server dev:fund <address> --usdc 1000 --eth 1`. Tests need only Postgres
(server tests use their own `bluechip_test` database); chain tests run on the devnet. `pnpm devnet:capture`
rebuilds the devnet's state from the fork block in the root `.env.local` (needs `BASE_FORK_RPC_URL`); run it when
bluechip starts using a new contract.

`pnpm typecheck:tsc` runs the official `tsc` and is for CI. Agents use `pnpm typecheck`.

## Validation

Use the narrowest validation that covers the change, then `pnpm check` before pushing:

| Change          | Validation                                                                   |
| --------------- | ---------------------------------------------------------------------------- |
| Source or tests | `pnpm lint:fix`, `pnpm format`, `pnpm test <file>`, `pnpm typecheck`         |
| Contracts       | `forge fmt` (in `contracts/`), `pnpm contracts:test`, `pnpm contracts:build` |
| Docs only       | `pnpm format`                                                                |

Report every command you could not run.

## Tooling

Configuration lives at the root: `dprint.json`, `.oxlintrc.json`, `tsconfig.base.json` (compiler
options and the Effect language service), `tsconfig.packages.json` and `tsconfig.tests.json`
(project references), `vitest.config.ts`, `lefthook.yml`, `commitlint.config.ts`.

TypeScript is TypeScript 7 (tsgo), patched with the Effect language service by `pnpm install`
(`effect-tsgo patch`), so `pnpm typecheck` reports Effect diagnostics. Fix what they flag; silence
one only when the flagged pattern is the point, for the next line only
(`// @effect-diagnostics-next-line <rule>:off`). oxlint runs Effect's own rules
(`@effect-kit/oxc`): import modules (`effect/Effect`), not barrels; relative imports end in `.ts`;
`Array<T>`, not `T[]`. Never disable a rule file-wide.

Packages export their source during development (`"./*": "./src/*.ts"`) and their build when
published (`publishConfig.exports` → `dist`), so tests and type checks never need a build. Builds
are `tsc -b` plus Babel's pure-call annotations, so bundlers tree-shake them like Effect.

## Repository scripts

Every repository script is a command of the Effect CLI in `scripts/`: `scripts/commands/<name>.ts`,
registered in `scripts/cli.ts` and run as `node scripts/bin.ts <name>` (root `package.json` scripts
call it). No JavaScript under `scripts/`: `pnpm lint` fails on `.js`/`.mjs`/`.cjs` files there.

- Keep commands thin: flags and wiring in the command, logic in exported functions that
  `scripts/test/<name>.test.ts` tests with real temporary folders (`FileSystem.makeTempDirectoryScoped`).
- Fail with the CLI's errors (`CheckFailed` for problems found, `ToolFailed` for a tool that failed);
  `scripts/bin.ts` reports them and sets the exit code. Run other tools through the `Tools` service.
- Config files (`vitest.config.ts`, `commitlint.config.ts`) are plain TypeScript: their tools load
  them.

## Dependencies

- Root and development dependencies are exact versions; published packages declare ranges
  (`^4.1.5`) for `dependencies` and `peerDependencies`. `effect` is a peer of every library.
- The pnpm catalog holds versions more than one package.json uses.
- New releases must be a day old before they install (`minimumReleaseAge`), except `effect`,
  `@effect/*` and `@effect-kit/*`. Dependency install scripts are denied unless listed in
  `allowBuilds`.

## Code guidelines

Load the `effect-conventions` skill before writing or reviewing code.

- Name things for what they are in the domain, consistently: one name per concept.
- Use what exists before writing a helper: Effect (`Array`, `String`, `Option`, `Schema`,
  `Predicate`, …), then the workspace's own modules. Never create catch-all `utils` or `helpers`.
- Inline one-off logic; extract only substantial or reused logic into a specifically named module.
- Every export of a published package has TSDoc with `@since`, `@category` and `@stability`, and
  examples as `**Example** (Title)` sections with a `ts import.meta.vitest` fence.
- Comments explain why, not what, and only where strictly needed (non-obvious reasons, invariants, external
  constraints); never restate the code.
- Separate logical blocks with blank lines: steps inside a function (read, check, write, return), groups of related
  declarations, so code reads in paragraphs.

### Files and folders

Code is organized so a maintainer can find and review any change quickly.

- Keep every source and test file around 500 lines or less. When one grows past that, split it along logical lines
  (one feature, screen section or concern per file), never at an arbitrary line.
- Group files into folders by feature or domain, not by kind: `apps/server/src/auth/`, `accounts/`, `api/`;
  `apps/web/src/routes/welcome/`, `shell/`, `atoms/`; a large page's sections in `apps/uikit/src/pages/<page>/`.
- Tests mirror the source tree (`test/api/` for `src/api/`), with shared test helpers in `test/support/`.

### Screens

The brand kit artifact (`kit/views/screens.js` and `screens.css`) is the reference for every screen: follow its
layout and copy with the components of `@bluechip/ui`. Never ship its example scaffolding (`Example` flags,
example patterns, simulated actions or fake data); show real data or an honest empty state.

Copy never uses a middle dot (`·`) as a separator. Write it as people speak: a sentence, commas or joining words
("Chainlink $152.04, 0.3% apart", "Locked with Face ID until 21 Feb", "$50 of Nvidia").

## Agents and policies

An agent is a session key carrying onchain policies; nothing offchain limits it. Its definition is an `AgentSpec`
(`packages/domain/src/policies/`): the catalog's policies with their configurations. bluechip decides on an operation
by simulating it as the agent (`simulateAsAgent` in `packages/chain/src/policies/`) and reading the chain's answer;
never write a TypeScript copy of a contract's rule.

To add a policy:

1. **Contract.** An outcome rule is a contract implementing `IOutcomeRule` in `contracts/src/rules/` (stateless
   rules are `pure`; state is keyed by `(guard, key, account)`), with Foundry tests and a gas check; add it to
   `RULES` in `scripts/contracts/artifacts.ts`. Another kind of policy is its own contract, or one of Namera's.
   `pnpm contracts:build`, then `pnpm devnet:capture`.
2. **Domain.** A module in `packages/domain/src/policies/` made with `Policy.make`: id, kind, copy (title, summary,
   aliases and examples for the assistant), a config Schema, a `Field` hint per config field (the web's generic
   editor and the range check use them), defaults, cross-policy `validate`, `describe` and `compare`. Register it in
   `POLICIES` (`AgentSpec.ts`), in the order `TradeGuard` runs rules. Add it to templates where it belongs.
3. **Chain.** A rule's binding in `packages/chain/src/policies/Rules.ts` (address, ABI, config encoding, a sentence
   per error); another kind is compiled in `Session.ts` (`compileSession`, `placements`), with its usage in
   `Usage.ts` if it counts something.
4. **Tests.** The conformance tests (`packages/domain/test/policies/Conformance.test.ts`,
   `packages/chain/test/policies/Conformance.test.ts`) check it once registered; add its refusal to
   `packages/chain/test/policies/Policies.test.ts` and its rules to `Catalog.test.ts`.
5. **Web.** A dedicated editor only if the generic one built from its fields isn't enough.

## Tests

Tests live in each package's `test/` folder and use `@effect/vitest` (`it.effect`, `assert`), never
`vitest` directly. `packages/ui` tests run in real Chromium (Vitest browser mode, `vitest-browser-react`) and
import the package by name (`@bluechip/ui/components/button`). Write the tests a behaviour needs: the documented contract, its failure cases and
regressions; leave what the type checker proves to `typetest/`. The landmines testing rules are
enforced: no test doubles (use real implementations, test layers, MSW for the network), no fixed
sleeps (`TestClock`, or await a signal), no polling races, and no retries or raised timeouts.

Chain tests run on the devnet (`packages/devnet`): a local Base with every contract bluechip uses at its real
address, one Anvil and Alto per Vitest worker, started from a captured state file, so they need no fork, no RPC and
no Docker. Only `pnpm test:fork` (not part of `pnpm check`) reads the real chain, to check the facts the devnet copies.

### Writing tests

Every test guards one intended behaviour: it fails on a regression of that behaviour and on nothing else.

- **Fastest level that proves it.** Pure function, then service, then API or component, then browser. A decision
  (a branch, a calculation, a parse) is a pure function with a domain name, tested directly with a table of
  examples; services, handlers and chain flows keep one test per outcome, not per case of a decision.
- **One example per test**, differing from its neighbours in one visible way that the name says. `describe` is the
  function, service or route (`describe("POST /api/trades")`, then the method); each `it` names the example (`"a
  buy over the daily budget"`, `"409: a confirm replayed"`). Reading only the names lists what is covered.
- **Input, call, output.** Write the input and the expected value out as literals in the test, call once, and
  compare the whole value (`assert.deepStrictEqual(result, expected)`), one assertion per thing checked: what came
  back, then each effect. Never derive the expected value with the code's own logic. A value the test can't know
  (an id, a hash, a time) is matched by its shape (a pattern), never by "any".
- **Cover every case** of each public function: every branch, each bound just inside, on and just outside, empty
  and full input, every failure the caller can see, repeats (the same call twice), and every setting it reads.
- **Isolated data.** Each test makes its own records (a new user, account or id) and reads back only those, so the
  suite passes shuffled, alone and in parallel. Arrange through the front door: the API's routes, the service's
  methods, the devnet's controls; never by reaching into private state.
- **No doubles of our own code.** Real implementations inside the process; at the edge, test layers and MSW (or the
  devnet for the chain). Assert state and results, not which internals were called.
- **Prune** a test that guards nothing: one that asserts removed code stays gone, what the type checker or a
  library already guarantees, a mock's own answer, private state or call order, or anything another test already
  proves (keep the faster one). Delete production code that only existed for a pruned test.
- **A bug found while testing** is not fixed in a refactor: pin today's behaviour in a test, add the right
  behaviour next to it as `it.skip("… (bug: …)")`, and report it.
- **Budgets:** about 5 ms for a pure function, 50 ms for a database or devnet round trip, 100 ms for an API request;
  one-time setup (migrations, starting the devnet) goes in `globalSetup` or `beforeAll`, never in each test.

## Commits and pull requests

Conventional Commits with kebab-case scopes (`feat(core): add retries`); commitlint checks commits
and the `PR title` workflow checks PR titles, because PRs are squash-merged.

## Subagents

Pick a subagent's model by how hard the task is. Easy or mechanical work (moving or splitting files, renames,
applying a known pattern, formatting, simple lookups) goes to a fresh subagent on Sonnet with a complete brief: the
files, the pattern, how to verify, what to report. Use Opus subagents only for work that needs hard thinking
(architecture, tricky debugging, security review, new design). Forks run on the parent's model, so don't fork easy
tasks.
