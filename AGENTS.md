## Workspace map

Dependencies point inward: apps depend on packages, packages never depend on apps.

| Path              | Package            | What it is                                          |
| ----------------- | ------------------ | --------------------------------------------------- |
| `packages/domain` | `@bluechip/domain` | Ids, errors, live events, the HTTP API contract     |
| `packages/chain`  | `@bluechip/chain`  | Base from Effect: client, deployments, ABIs, owners |
| `packages/devnet` | `@bluechip/devnet` | A local Base for tests, per Vitest worker           |
| `packages/ui`     | `@bluechip/ui`     | The design system, presentational only              |
| `apps/web`        | `@bluechip/web`    | The TanStack Start web app                          |
| `apps/server`     | `@bluechip/server` | The Effect v4 HTTP server and background work       |
| `apps/uikit`      | `@bluechip/uikit`  | Every `@bluechip/ui` component, link previews       |
| `apps/e2e`        | `@bluechip/e2e`    | The browser end-to-end suite (Playwright)           |
| `contracts/`      | –                  | Onchain policies in Solidity (Foundry, Soldeer)     |
| `content/help/`   | –                  | The help center's articles                          |
| `scripts/`        | `scripts`          | Tooling, one Effect CLI (`node scripts/bin.ts`)     |
| `deploy/`         | –                  | Dokploy's compose files, guide, env files           |

Every package and app is private; packages keep a publishable shape, each with its own public boundary. In
more detail:

- **`packages/domain`**: the server implements `BluechipApi` (Effect `HttpApi`), the web app calls it. Depends only on
  `effect`.
- **`packages/chain`**: `ChainClient` (viem); each network's `Deployment` (`deployments/`: USDC, EntryPoint, the
  exchange, every stock with its feed and pool, bluechip's policies, the explorer; `local` is Base's, `sepolia`
  paper's), read through `ChainDeployment` (from `NETWORK`), never module constants; shared ABIs; the account's owners
  and recovery sessions (`account/`); `DevChain` cheatcodes for the local fork.
- **`packages/devnet`**: started from a state captured once from a fork (`state/devnet.state.gz`, rebuilt by
  `pnpm devnet:capture`), its clock kept at the real one (`keepClock`: on Base's hardfork Anvil dates each block
  200 ms after the last), with every contract bluechip uses at its real address and settable price feeds (`Devnet`,
  `DevnetTest`), software passkeys (`Passkeys`), calls simulated at a later block time (`simulateAt`,
  `handleOpsCall`), and a devnet of a test file's own whose clocks can move ahead (`DevnetTest.layerIsolated`,
  `DevnetClock`).
- **`packages/ui`**: Tailwind v4 theme, base components on Base UI, bluechip's product components, motion and
  illustrations.
- **`apps/server`**: Postgres through Drizzle ORM (1.0 RC, Effect driver); SQL migrations in `apps/server/drizzle/`
  generated by `drizzle-kit`, never edited by hand. The one exception: the durable engine's `cluster_*` tables,
  created by Effect's own migrations and excluded from drizzle-kit (`tablesFilter`). Background work (crons,
  workflows, entities) runs on Effect's cluster engine in the server (`apps/server/src/platform/engine/`).
- **`apps/uikit`**: a TanStack Router single-page app (`pnpm --filter @bluechip/uikit dev`, port 4000). Its `/social`
  page holds the web app's link previews and icons, which `node scripts/bin.ts og` renders into `apps/web/public/`
  (rerun it after changing them; the PNGs are committed).
- **`apps/e2e`**: the web app in Chromium against the real server and its own devnet, with a virtual passkey
  authenticator (`pnpm test:e2e`, see its README and [below](#chain-and-browser-suites)).
- **`contracts/`**: `AerodromeTradePolicy` (validation), `TradeGuard` (execution: measures what moved, values the
  portfolio, then runs the session's rule contracts, `src/rules/*Rule.sol`), `RecoveryDelayPolicy` (a recovery key's
  owner changes wait 48 hours), Namera v2 policies, deployed by CREATE2 at the same address everywhere.
  `contracts build` writes their addresses and ABIs to `packages/chain/src/policies/Deployed.ts`. `test/vectors.json`
  is a frozen fixture of the rules' behaviour. A change to their bytecode moves their addresses: rebuild, then
  `pnpm devnet:capture`, and update the gas snapshot (`node scripts/bin.ts contracts snapshot`). A new contract alone
  needs no capture: `pnpm devnet:deploy` adds what's missing to the captured state, as the capture would.
- **`content/help/`**: one Markdown file per article (`# Title`, then `## Section`s). The server's knowledge
  (`apps/server/src/modules/knowledge/`) chunks them by section for the assistant's `searchHelp`, refreshed at start
  and daily; write only what the app does today.
- **Probes and throwaway work** go in `research/scratchpad/` (`research/` is git-ignored, locally through
  `.git/info/exclude`): run with `node`, deleted afterwards. Never anywhere else in the repository.

## Getting started and commands

| Command                | What it does                                                         |
| ---------------------- | -------------------------------------------------------------------- |
| `pnpm dev`             | Every local service in one terminal (below); `pnpm dev:stop` stops   |
| `pnpm check`           | Everything CI runs, in order. Run it before every push.              |
| `pnpm typecheck`       | Type-check everything with tsrs (TypeScript 7 + Effect diagnostics)  |
| `pnpm lint`            | oxlint with Effect's rules, and which way imports point (`lint:fix`) |
| `pnpm format`          | Format with dprint (`format:check` only checks)                      |
| `pnpm test`            | Run every Vitest project once (`test:watch` for watch mode)          |
| `pnpm test:e2e`        | The browser end-to-end suite on its own stack (slow, not in `check`) |
| `pnpm test:fork`       | Deploy the policies to a running fork, then check real-Base facts    |
| `pnpm contracts:test`  | Format check, lints and Foundry tests of `contracts/`                |
| `pnpm contracts:build` | Build `contracts/` and regenerate `Deployed.ts`                      |
| `pnpm devnet:capture`  | Rebuild the devnet's state from a fork (`devnet:deploy` adds to it)  |
| `pnpm build`           | `tsc -b`, then each package's build                                  |
| `pnpm circular`        | Fail on import cycles between modules                                |

`pnpm typecheck:tsc` runs the official `tsc` and is for CI. Agents use `pnpm typecheck`.

### Local development

Each app keeps only `.env.example` (committed) and `.env.local` (never committed); paper's and production's settings
live in `deploy/` ([Deploy](#deploy)). Copy each `.env.example` to `.env.local`:

- the root's: Docker Compose's fork RPC; `pnpm devnet:capture` reads the fork block there (needs `BASE_FORK_RPC_URL`);
- `apps/server`'s: `AGENT_KEY_ENCRYPTION_KEY` from `openssl rand -base64 32`, web push keys from
  `node scripts/bin.ts vapid --env apps/server/.env.local` and, for the Telegram bot, `TELEGRAM_BOT_TOKEN` and
  `TELEGRAM_BOT_USERNAME` (polling for updates in development);
- `apps/web`'s.

Then `pnpm dev` runs Postgres, the local chain (the devnet on Anvil, 8545, no RPC; its feeds and pools follow the
server's market prices every 15 s, and its state carries over between runs in `.data/devnet/`), the Alto bundler
(4337), migrations, then the server (8080), the web app (3000) and the component kit (4000). Ctrl+C stops everything;
`pnpm dev:stop` stops anything left running (`--all` stops Postgres too).

| Flag                       | Effect                                                 |
| -------------------------- | ------------------------------------------------------ |
| `--fork`                   | An Anvil fork of Base through your RPC, not the devnet |
| `--reset-chain`            | Start the local chain again from the capture           |
| `--no-chain`, `--no-uikit` | Skip those parts                                       |

Fork money: `pnpm --filter @bluechip/server dev:fund <address> --usdc 1000 --eth 1`. Tests need only Postgres (server
tests use their own `bluechip_test` database); chain tests run on the devnet. Run `pnpm devnet:capture` when bluechip
starts using a new contract.

### Paper money

Paper money is `NETWORK=sepolia`: Base Sepolia, test dollars at live prices. Its settings are `deploy/.env.paper`
(git-ignored, never printed), which every workstation command reads:

- `node scripts/bin.ts contracts deploy --network sepolia` deploys the paper contracts (`contracts/src/paper/`) and
  bluechip's policies with `OPERATOR_PRIVATE_KEY` and rewrites `packages/chain/src/deployments/Sepolia.ts`
  (`BASESCAN_API_KEY` there is for this command's source verification only).
- The server on paper needs the operator's key (it refuses to start without it, or with another): `modules/paper/`
  writes the feeds from Alpaca's prices every 15 s while the market trades (0.1% moves or hourly; `PaperFeeds`, a
  cluster singleton, off with `SCHEDULES_ENABLED=false`) and mints the faucet's test USDC (`modules/faucet/`,
  `GET`/`POST /api/faucet`, $10,000 a day per account; on `local` it sends from the devnet, on Base it answers
  `Forbidden`), one operator transaction at a time.
- Gas is Alchemy's (`BUNDLER=alchemy`; its endpoints follow the chain, `base-sepolia` here) with bundler sponsorship
  (`GAS_SPONSORSHIP=alchemy-bso`, the Gas Manager policy's type).
- A local server on paper runs on a database of its own, given ahead of the file (whose `DATABASE_URL` is a
  placeholder, and which never overrides a set variable), and must not take over the paper bot's updates, so leave
  the `TELEGRAM_*` lines out:
  `DATABASE_URL=postgres://… node --env-file=<(grep -v '^TELEGRAM_' deploy/.env.paper) apps/server/src/bin/migrate.ts`,
  then `src/main.ts` the same way. The web app: `pnpm --filter @bluechip/web exec vite dev --mode paper --port 3000`
  (modes `paper`, `production` and `landing` read `deploy/.env.<mode>`, `envDir` in `apps/web/vite.config.ts`).

### Preview mode

For reviewing the UI: `pnpm dev:preview` runs only the web app and opens `/home?preview=typical`. With `?preview` (or
`?preview=newPerson`, `typical`, `heavy`; `?preview=off` leaves it) the app talks to a mock of `BluechipApi` served in
the browser from a made-up world (`apps/web/src/preview/`: the cast of each scenario in `world/cast.ts`, a slice per
area in `world/`, the mock's handlers in `server/`), with fake Face ID. The god mode panel (the pill in the corner, or
⌘.) switches the account, puts agents, trades, automations, chats and the account in any state, and slows, hangs or
breaks any area's requests. Only `client.tsx` loads it, in development (`pnpm lint` fails on any other import of
`preview/`), so it never ships. Tests in `apps/web/test/unit/preview/` decode every mocked answer with the real API: a
change to the API that the mock doesn't follow fails them.

### The software passkey

For driving the real app without Touch ID (an agent in a browser): in development, `?softPasskey` (kept in local
storage until `?softPasskey=off`) answers every WebAuthn prompt with a real P-256 authenticator in the page
(`apps/web/src/preview/softPasskey/`): none attestation, ES256 DER signatures with low S, counters, allow and exclude
lists. Its keys ("Owner 1", "Recovery key 1") live in local storage, so the account outlives reloads; a discoverable
sign-in with several keys asks which in a dialog (newest first), and the badge in the bottom-right corner lists them,
forgets them or turns it off. The server and the chain's `WebAuthnValidator` verify its signatures as any passkey's.
It loads like preview mode (only from `client.tsx`, in development, never with `?preview`).

## Validation

Use the narrowest validation that covers the change, then `pnpm check` before pushing:

| Change                            | Validation                                                                   |
| --------------------------------- | ---------------------------------------------------------------------------- |
| Source or tests                   | `pnpm lint:fix`, `pnpm format`, `pnpm test <file>`, `pnpm typecheck`         |
| A screen, a flow or the web's API | Then `pnpm test:e2e` (the affected specs)                                    |
| Contracts                         | `forge fmt` (in `contracts/`), `pnpm contracts:test`, `pnpm contracts:build` |
| Docs only                         | `pnpm format`                                                                |

Report every command you could not run.

## Conventions

### Code

Load the `effect-conventions` skill before writing or reviewing code.

- Name things for what they are in the domain, consistently: one name per concept.
- Use what exists before writing a helper: Effect (`Array`, `String`, `Option`, `Schema`, `Predicate`, …), then the
  workspace's own modules. Never create catch-all `utils` or `helpers`.
- Inline one-off logic; extract only substantial or reused logic into a specifically named module.
- Every export of a published package has TSDoc with `@since`, `@category` and `@stability`, and examples as
  `**Example** (Title)` sections with a `ts import.meta.vitest` fence. Export only what another module imports.
- Comments explain why, not what, and only where strictly needed (non-obvious reasons, invariants, external
  constraints); never restate the code.
- Separate logical blocks with blank lines: steps inside a function (read, check, write, return), groups of related
  declarations, so code reads in paragraphs.

### Effect

bluechip is written the way Effect writes Effect: read the analogue in `node_modules/effect/ai-docs` (or the reference
clone `~/.cache/effect-reference`) before inventing a shape.

- **Schemas own their codecs.** Never write `encodeX`/`decodeX` pairs or module-level
  `XJson = Schema.toCodecJson(X)` constants. JSON in Postgres is a schema-typed column (`jsonbSchema(AgentSpec)` in
  `apps/server/src/platform/db/columns.ts`), so rows carry domain values; other boundaries decode where the value
  enters (`Schema.decodeUnknownEffect(X)(input)`), with the schema written at the call.
- **Behaviour lives in services.** Logic that reaches for other services is a `Context.Service` with a `layer` (and a
  `layerNoDeps` when tests swap a dependency, `layerTest` for an in-memory version), built with `Effect.gen` and
  `Effect.fn("Service.method")`. Don't export free-standing effect functions that `yield*` services from a module of
  loose functions; group them into the service that owns the data (`IntentStore`, `AgentSessions`, `AuditLog`).
- **Inline one-offs.** A function used once is written where it is used. Extract only what is reused, or what names a
  domain concept worth a name, into a module named for that concept. Pure domain decisions (a calculation, a
  transition) stay pure functions in `packages/domain`, tested directly.
- **Rows to domain values** are mapped inside the service that owns the table, not in `*Records.ts` modules of loose
  functions.
- **HTTP handlers** take their services once:

  ```ts
  HttpApiBuilder.group(Api, "group", Effect.fn(function*(handlers) {
    const agents = yield* Agents
    return handlers.handleAll({ ... })
  }))
  ```
- **Errors** are tagged (`Schema.TaggedError`), failed with `return yield* new Error(...)`, and translated at the
  boundary that knows better (`Effect.catchTag`), never swallowed.

### Files and folders

Code is organized so a maintainer can find and review any change quickly.

- Keep every source and test file around 500 lines or less. When one grows past that, split it along logical lines
  (one feature, screen section or concern per file), never at an arbitrary line.
- Group files into folders by feature or domain, not by kind: `apps/server/src/modules/auth/`, `modules/accounts/`;
  `apps/web/src/features/agents/`, `features/stocks/`; a large page's sections in `apps/uikit/src/pages/<page>/`.
- Import modules directly; no `index.ts` barrels anywhere.
- Tests are split by tier, each mirroring the source tree ([Test layout](#test-layout)).

### Web app layout

`apps/web/src` is feature-first (after Bulletproof React):

- `routes/`: TanStack Router's route files only: `createFileRoute`, params and search validation, loaders, and a
  component that renders a feature's screen. No screen bodies and no `-components` folders (TanStack allows them; we
  keep one place per feature so routes stay thin).
- `features/<feature>/`: everything one feature owns: `screens/` (what routes render), `components/`, `hooks/`,
  `atoms/` (its queries and mutations) and `model/` (pure logic and wording, no React).
- Shared, for what two or more features use: `components/` (`layout/` holds the page frames), `hooks/`, `atoms/`
  (queries several features read: the user, stocks, portfolio, agents, activity), `lib/` (the API client and live
  events, passkey signing, amounts, wallet config: the chain is read through the server's `/api/rpc`, never a node of
  its own) and `providers/`.
- Screens build on the shared pieces rather than their own copies: `StatusPill` (`@bluechip/ui`) for every state, with
  its words from one map per concept in `lib/` (`intentStatus.ts`, `agentState.ts`, `automationWords.ts`,
  `activityText.ts`); `useAgentState` for an agent's pill and dot; `LoadProblem`, `IllustratedEmpty`, `SectionHeader`
  (`layout/`), `ConfirmDialog`, `WhoChip`, `FilterTabs` and `fields/`; `passkeyProblem` for a Face ID that didn't
  finish; times in the viewer's zone, named (`yourTime`, `dailyResetText` in `lib/localTime.ts`).

Imports flow one way: shared → `features` → `routes`. Features never import each other or routes, and shared code
never imports features. When a screen shows another feature's piece, its route composes them, passing the piece in as
a prop (the agent page's trade and activity sections, the home page's approvals bell, the app frame's sidebar).

Every route names its page in `head()` with `pageHead` (`lib/seo/`): `Portfolio | bluechip`, a public page's canonical
URL and its social image. Only production's public pages (landing, help, legal) are indexed; signed-in pages, paper
money and local are `noindex`. The build's network (`VITE_NETWORK`, `VITE_SITE_URL` for another origin) decides
`robots.txt`, `manifest.webmanifest` and production's `sitemap.xml`, written by the Vite config's
`bluechip:crawler-files` plugin (and served by `vite dev`) with the files for agents (`lib/seo/llms.ts`): `llms.txt`,
`llms-full.txt` and a Markdown twin of every public page (`/index.md`, `/help.md`, `/help/<slug>.md`, `/legal/*.md`),
linked from its head (`pageHead({ markdown: true })`). The help center (`features/help/`) publishes each
`content/help/*.md` at `/help/<slug>`, its sections anchored as the assistant cites them (`anchorOf`), dated from git.

The web app ships as static files: `pnpm --filter @bluechip/web build` (production's settings from
`deploy/.env.production`, or `--mode paper` for `deploy/.env.paper`) prerenders the public pages (`/`, `/help`,
`/help/*`, `/legal/*`) to `dist/client/**/index.html` with their head, and writes `dist/client/_shell.html`, the SPA
shell (the root's `noindex` tags) for every other path. A new public page goes in `pages` in
`apps/web/vite.config.ts`. Serve `dist/client` with Caddy (the image's is `apps/web/Caddyfile`); the server has its
own domain (`VITE_API_URL`):

```caddy
bluechip.markets {
  root * /srv/bluechip/web
  try_files {path} {path}/index.html /_shell.html
  file_server
}
```

Paper's site can add `header X-Robots-Tag "noindex, nofollow"` for crawlers that never read the pages.

### Server layout

`apps/server/src` is ports and adapters, packaged by feature (after Effect's server fixture in
`node_modules/effect/ai-docs/src/51_http-server/fixtures/server/`, Cockburn's hexagonal architecture and package by
feature): a `Context.Service` is a port, a `Layer` its adapter.

- `modules/<feature>/`: one folder per feature (`accounts`, `activity`, `agents`, `analytics`, `assistant`, `audit`,
  `auth`, `automations`, `channels`, `dev`, `events`, `faucet`, `funding`, `intents`, `journal`, `knowledge`,
  `ledger`, `market`, `memory`, `notifications`, `paper`, `performance`, `policies`, `portfolio`, `push`, `recovery`,
  `rpc`, `signing`, `system`, `telemetry`, `trading`): its services (`Agents.ts`, `AgentSessions.ts`), its HTTP
  handlers (`http.ts`), its Drizzle tables (`tables.ts`) and its crons.
- `platform/`: infrastructure the features share: `db/` (`Database`, columns, `schema.ts` gathering every table for
  drizzle-kit), `embeddings/`, `engine/`, `http/` (middleware, health), `live/` (`LiveEvents`), `namera/`,
  `telemetry/` (exporters, tracer, metrics, the web app's telemetry proxy). `config/` holds `AppConfig`, logging and
  the release.
- `Api.ts`, `Services.ts` (`ServicesLive`), `Server.ts` and `main.ts` are the composition root, the only place
  production layers are wired; `bin/` holds the CLI entrypoints.

Modules use `platform/` and other modules' services and tables, never another module's `http.ts`; `platform/` never
imports `modules/` (except `platform/db/schema.ts`).

### Screens and copy

The brand kit artifact (`kit/views/screens.js` and `screens.css`) is the reference for every screen: follow its layout
and copy with the components of `@bluechip/ui`. Never ship its example scaffolding (`Example` flags, example patterns,
simulated actions or fake data); show real data or an honest empty state.

Copy never uses a middle dot (`·`) as a separator. Write it as people speak: a sentence, commas or joining words
("Chainlink $152.04, 0.3% apart", "Locked with Face ID until 21 Feb", "$50 of Nvidia").

## Domain guides

### Trades and intents

Every trade, yours or an agent's, is an **intent** (`packages/domain/src/intents/`,
`apps/server/src/modules/intents/`): who asked, who signs (the agent's key or your passkey), the trade, why, what was
decided and how it ended.

- An agent's intent runs as an `ExecuteIntent` workflow whose steps go through the account's `AccountDesk` (one at a
  time per account): over the agent's largest trade it waits for your approval; otherwise it is simulated as the
  agent, then sent by the agent's key, or blocked with the refusing policy in words, or left waiting (prices, gas, the
  day's last minute).
- A plan of several trades (an automation's run) is one batch (`batch_id`) in waves (`waves` in
  `packages/domain/src/intents/Batch.ts`, one leg per stock, since `TradeGuard` judges each stock's net move): the
  desk sends a wave's legs in one operation, after the plan's earlier waves, and decides them one by one when the
  batch as a whole doesn't pass; approving one of a batch prepares its other waiting legs for the same signature.
- Your own trades and approvals are prepared for your passkey and sent by `Trades`.

Never send money any other way; new sources (the assistant, automations, chat platforms, MCP) create intents through
`Intents`.

### Owners and recovery

The account's owners are passkeys on Namera's `WebAuthnValidator` (Kernel's root validator) with a threshold of one:
any of them signs, so signing requests accept any active owner and build the account at its stored address. Adding or
removing an owner is one owner operation (`account/Owners.ts`); the last one can't be removed.

A recovery passkey is a Namera session (`account/Recovery.ts`) that may only ask for owner changes and make them
through `RecoveryDelayPolicy`, which returns the request's due time as `validAfter`: the 48-hour delay is enforced
onchain. bluechip's guard key (sealed like agents' keys) may only cancel a request, so any signed-in device or Telegram
can cancel without Face ID. A compromised server can cancel recoveries, never start or speed one.

Testing it: Alto checks `validAfter` against the wall clock, so chain tests prepare a due recovery as it would be later
(`TestAgents.sessionFor` with `secondsAhead`) and simulate the EntryPoint at that time (`Devnet.simulateAt`). Never
move the shared devnet's clock or revert a snapshot, which every suite sharing the worker's Anvil would see (on Base's
hardfork Anvil never moves its clock back). A test that needs time to pass runs on a devnet of its own: server tests
on `TestUsers.layerIsolated` (or `TestAgents.layerIsolated`, `TestRecovery.layerIsolated`), whose `TestClocks` moves
the chain, Alto and the server ahead together, as the due recovery's test does.

### Ledger and performance

Every fill goes to the ledger (`apps/server/src/modules/ledger/`) from `TradeLedger.settle`: its costs (the pool's
fee, slippage against the trade's Chainlink reference, gas from the receipt), then its stock's lots rebuilt FIFO from
that stock's fills and adjustments (`replay` in `packages/domain/src/ledger/Lots.ts`), then the day's `pnl_daily` rows.
The ledger is always a replay, so backfill and repair are the same code (`Ledger.repair`, at startup and hourly).

Every 5 minutes `Reconciliation` compares each account's balances on chain with its ledger: USDC transfers in are
deposits (the `deposit` notification), anything else is a flagged adjustment with a `balanceUnexplained` alert
(`RECONCILE_ENABLED=false` turns the schedule off; tests call `check` per user). `Performance` reads it all for the
API, the pages and the assistant's read tools. Never compute profit, cost basis or costs anywhere else.

### Agents and policies

An agent is a session key carrying onchain policies; nothing offchain limits it. Its definition is an `AgentSpec`
(`packages/domain/src/policies/`): the catalog's policies with their configurations. bluechip decides on an operation
by simulating it as the agent (`simulateAsAgent` in `packages/chain/src/policies/`) and reading the chain's answer;
never write a TypeScript copy of a contract's rule.

Every session of one agent (its lock, each change, each renewal with a new key) carries the same `agentKey(agentId)`
(`packages/chain/src/policies/Session.ts`): `AerodromeTradePolicy` keys the day's spending by it and `TradeGuard` its
rules' state, so a renewal keeps what the agent spent today; Namera's trade count and gas are the session's. Removing
an agent deletes its automations and its expiry pauses them, in the transaction of the agent's change
(`AgentStore.save`).

To add a policy:

1. **Contract.** An outcome rule is a contract implementing `IOutcomeRule` in `contracts/src/rules/` (stateless rules
   are `pure`; state is keyed by `(guard, key, account)`), with Foundry tests and a gas check; add it to `RULES` in
   `scripts/contracts/artifacts.ts`. Another kind of policy is its own contract, or one of Namera's.
   `pnpm contracts:build`, then `pnpm devnet:capture`.
2. **Domain.** A module in `packages/domain/src/policies/` made with `Policy.make`: id, kind, copy (title, summary,
   aliases and examples for the assistant), a config Schema, a `Field` hint per config field (the web's generic editor
   and the range check use them), defaults, cross-policy `validate`, `describe` and `compare`. Register it in
   `POLICIES` (`AgentSpec.ts`), in the order `TradeGuard` runs rules. Add it to templates where it belongs.
3. **Chain.** A rule's binding in `packages/chain/src/policies/Rules.ts` (address, ABI, config encoding, a sentence
   per error); another kind is compiled in `Session.ts` (`compileSession`, `placements`), with its usage in `Usage.ts`
   if it counts something.
4. **Tests.** The conformance tests (`packages/domain/test/unit/policies/Conformance.test.ts`,
   `packages/chain/test/{unit,integration}/policies/Conformance.test.ts`) check it once registered; add its refusal to
   `packages/chain/test/integration/policies/Policies.test.ts` and its rules to
   `packages/domain/test/unit/policies/Catalog.test.ts`.
5. **Web.** A dedicated editor only if the generic one built from its fields isn't enough.

### Automations

An automation is a trigger, conditions and an action, saved for you or an agent; its runs end as intents
(`packages/domain/src/automations/`, `apps/server/src/modules/automations/`). Triggers, conditions and actions are
catalogs like the policies'.

To add a trigger, condition or action:

1. **Domain.** A module in `packages/domain/src/automations/triggers/`, `conditions/` or `actions/` made with the
   catalog's `make` (`Trigger.make`, `Condition.make`, `Action.make`, on top of `Entry.make`): type, copy (title,
   summary, aliases and examples for the assistant), a config Schema, a `Field` hint per config field (units in
   `Entry.ts`), defaults, `check` against the agent it runs for, and `describe`. A trigger also says its `watcher`,
   `marketHours` and `asks`; a condition its pure `evaluate` over `Facts` (`null` for one that needs a model, as
   `judgment`); an action its `plan` of legs (`null` when it trades nothing). Register it in `TRIGGERS`, `CONDITIONS`
   or `ACTIONS` (`Automation.ts`); the stored unions and the API's catalog follow.
2. **Runtime.** A trigger needs its watcher to produce it: schedule, price, portfolio or news in
   `apps/server/src/modules/automations/watchers/`, keeping its memory in `WatchState`; a new kind of watcher is wired
   in `Services.ts`. Conditions run in `AutomationRunner`, trades are planned by `Planner.ts` (`planLegs`); nothing
   else changes for a new condition or action.
3. **Tests.** The conformance tests (`packages/domain/test/unit/automations/Conformance.test.ts`) check every
   registered entry; add the entry's own table in `test/unit/automations/{triggers,conditions}/` (or
   `Planner.test.ts`) and, for a trigger, its watcher's test in `apps/server/test/integration/modules/automations/`.
4. **Web.** Nothing, when its `Field` hints say how to edit it: the generic editor and the automation sentences are
   built from the catalog. Add a dedicated editor only when a field's unit can't (as the `stopLossFloor` policy's price
   per stock).

### Notifications

Features never send messages. They say what happened: an event written to the notifications' outbox
(`NotificationOutbox.write`, or `notify` for a draft written as it is) in the transaction of the change it tells, then
published live (`LiveEvents`), which wakes `NotificationFanout` to turn the user's outbox rows into notifications (at
least once; `OutboxCron` sweeps what a stopped process left). Only what time makes (`Reminders.ts`) calls
`Notifications.add` itself. `Notifications` stores it in your center once (`dedupe_key`), publishes
`NotificationAdded`, and starts a `DeliverNotification` workflow per channel its rule picks (quiet hours wait on a
durable clock; a platform that says try again is retried). Domain in `packages/domain/src/notifications/` and
`channels/`, server in `apps/server/src/modules/notifications/`, `push/` and `channels/`.

To add a notification kind:

1. **Domain.** Add it to `NotificationKind` (`Notification.ts`) and `KINDS` (`Kinds.ts`): group, label, description,
   severity (`security` locks it on every channel), the channels it may use and its defaults. Write its draft in
   `Drafts.ts` (account safety in `SecurityDrafts.ts`), a pure function of what happened with a `dedupeKey`, tested
   with a table in `test/unit/notifications/`. A kind that offers an action where it lands (Pause all, Cancel
   recovery) says so in `actionsOf` (`Actions.ts`): the bell and Telegram show its buttons.
2. **Server.** Make it from an outbox event in `Fanout.ts`, from time in `Reminders.ts`, or with
   `NotificationOutbox.notify` in the transaction of the change. Never call a notifier.
3. **Web.** Nothing: the settings page and the bell are built from the catalog.

To add a notifier (a channel):

1. **Domain.** Add it to `Channel` and to the kinds that may use it (`KINDS`), and its words if a notification reads
   differently there (as `chatNotification` in `channels/ChatCards.ts`).
2. **Server.** A service with `send(userId, notification)` answering `sent` or `skipped` (nowhere to send it), failing
   `NotifierError` (`retryable` when trying later can work); add its case to `Notifiers.ts` and its channel to
   `notification_deliveries.channel` (drizzle-kit migration). Test it at the platform's edge with an in-process
   `HttpClient` (as `PushServiceTest`).
3. **Web.** A column in the settings page follows `CHANNEL_LABELS`; a card for opting in, if it needs one.

To add a chat platform (Slack, Discord):

1. **Domain.** Add it to `Platform` (`channels/Channel.ts`) and as a channel (above).
2. **Server.** Its `effect/chat` adapter (`@effect/chat-<platform>`) registered in the chat router beside Telegram's
   in `modules/channels/<platform>/`, with its transport (webhook route or socket, one consumer) wired in `Server.ts`.
   `ChatBot`, `BotHandlers` (the `AnswerChatMessage` workflow, `BotInteractions`) and `ChatNotifier` are
   platform-free: linking, the assistant (`surface` is the platform; tools keep their risk levels: configure cards
   confirm with buttons, sign cards link into the app, nothing is signed in a chat), commands and notifications work
   as they are. Add the platform to `Surface` (`assistant/Conversation.ts`).
3. **Tests.** Conversations on `ChatTest` with the platform's capabilities (as `TelegramTest` in `TestServer.ts`,
   through `TestTelegram`), and the transport against an in-process API (as `BotApiTest`). Tests never reach the
   platform; a live probe goes in `research/scratchpad/` and is deleted after.

### Telemetry (Axiom)

Telemetry leaves the server only when `DEPLOYMENT_ENVIRONMENT` is `paper` or `production` and the Axiom settings are
set (`TelemetryConfig`); in development and tests nothing is exported. `TelemetryLive`
(`apps/server/src/platform/telemetry/`) exports traces, logs (beside the console's) and metrics over OTLP to their
Axiom datasets, flushed on shutdown.

Spans go through `BluechipTracer`: fast `BEGIN`/`COMMIT` and statements under 2 ms are dropped (their parent counts
them in `db.statements` and `db.time_ms`), kept statements are named `select intents`, a `GET` is sampled at
`TRACE_SAMPLE_READS` unless the browser's `traceparent` decides, and a tick in `TICKS` that sets `bluechip.idle` is
dropped whole. Server spans are named by route (`POST /api/trades/:id/confirm`); `isUntraced` routes (`/health`,
`/api/version`, `/api/events`, `/api/rpc`, `/api/sync/*`) make no spans at all. Chain calls are `chain.<operation>`
spans (`ChainClient.use`), bundler calls `bundler.<rpc method>` (`callBundler` in
`packages/chain/src/ChainTelemetry.ts`).

- **A span attribute**: `Effect.annotateCurrentSpan({ "intent.id": … })` where the value is known, from the names in
  use (`user.id`, `agent.id`, `intent.id`, `intent.source`, `batch.id`, `automation.id`, `conversation.id`,
  `trade.id`, `stock.symbol`, `trade.side`, `user_op.hash`). Every name is a column in Axiom (256 per dataset): reuse
  one before adding one. Never amounts of money you can't show, addresses, keys, prompts or message text.
- **A metric**: add it to the catalogue in `packages/domain/src/analytics/Metrics.ts` (name, kind, UCUM unit,
  attributes; the Axiom dashboards read it), declare it in `apps/server/src/platform/telemetry/Metrics.ts` with the
  same name and attributes (the conformance test compares them), and record it where the fact is known with `count`
  or `record`, after the change commits. Attributes stay low cardinality: never an id. Gauges that need a query go in
  `TelemetryGauges` (every minute, or hourly).
- **The web app's telemetry** goes through the server, never traced or logged per request: `POST /api/sync/{t,l,m}`
  (traces, logs, metrics; neutral paths, since ad blockers drop ones that look like telemetry) takes OTLP (JSON or
  protobuf, gzip or not, 1 MiB), stamps `deployment.environment` and `network` on resources without them and forwards
  it with the server's ingest token (`204` when Axiom is off, `429` past its rate per address). posthog-js sends to
  PostHog's reverse proxy on our own domain (`VITE_POSTHOG_HOST`), not through the server. The web app sends
  `x-bluechip-replay-session` (its PostHog replay session), which lands on the request span as `posthog.session_id`.

### Product analytics (PostHog)

The server tells PostHog the facts it owns through `Analytics` (`apps/server/src/modules/analytics/`): batched to
`/batch/` every 5 s or 100 events, retried, dropped with a warning after 3 tries, flushed on shutdown; only on paper
and production with `POSTHOG_PROJECT_API_KEY` (`layerNoop` elsewhere; tests read `AnalyticsTest`). Every event carries
`network`, `environment`, `app_version` and the `trace_id`. LLM analytics (`$ai_generation` from `Budgets.record`,
`$ai_span` per tool call and `$ai_trace` per turn in `Assistant`, `$ai_embedding` in `RecallIndex`) carries no prompt
or answer unless `LLM_ANALYTICS_CAPTURE_TEXT` is on.

- **An event**: add it to the catalogue (`packages/domain/src/analytics/ServerEvents.ts` or `WebEvents.ts`; the
  conformance test refuses forbidden property names: no addresses, names, balances, keys or text; exact dollars only
  on server money events). The server captures it with `analytics.capture(userId, event, { id, at })` in the service
  that owns the fact, **after** its transaction commits (where its metric is counted), never inside one. `id` is the
  fact's own id (a trade, an intent and its status, a run): the event's uuid is a UUIDv5 of it and the name, and `at`
  the fact's time, so a replayed step is one event in PostHog. Person properties go in `set` / `setOnce`
  (`PersonProperties` in `packages/domain/src/analytics/Person.ts`); `identify` sets them with no event. Add its case
  to the flow's test in `apps/server/test/e2e/analytics/`. The web sends its own events with `track`
  (`lib/analytics.ts`).

## Tests

Tests live in each package's `test/` folder and use `@effect/vitest` (`it.effect`, `assert`), never `vitest`
directly. `packages/ui` tests run in real Chromium (Vitest browser mode, `vitest-browser-react`) and import the package
by name (`@bluechip/ui/components/button`). Write the tests a behaviour needs: the documented contract, its failure
cases and regressions; leave what the type checker proves to `typetest/`. The landmines testing rules are enforced: no
test doubles (use real implementations, test layers, MSW for the network), no fixed sleeps (`TestClock`, or await a
signal), no polling races, and no retries. Timeouts stay at Vitest's default except the devnet-backed projects
(devnet, chain, server), which run as their own group with 15 s per test.

### Test layout

Every package's `test/` folder is split by tier; each tier mirrors `src/`:

| Folder              | Holds                                            | Runs against                        |
| ------------------- | ------------------------------------------------ | ----------------------------------- |
| `test/unit/`        | Pure functions and domain logic                  | Nothing: no IO                      |
| `test/integration/` | One service (or chain flow), real dependencies   | Postgres, the devnet                |
| `test/e2e/`         | The HTTP API through the typed client            | A test server, the devnet, Postgres |
| `test/fixtures/`    | Known values, builders (specs, legs, amounts)    | –                                   |
| `test/utils/`       | Test layers, harness (`TestServer`, `TestUsers`) | –                                   |
| `test/setup/`       | Vitest `globalSetup` files                       | –                                   |

The e2e tier's test server is `NodeHttpServer.layerTest`; `test/utils/` also holds `TestEvents` and `EngineTest`.

`apps/web` (project `web`) has a unit tier: `test/unit/` mirrors `src/` (`features/<feature>/model/`, `lib/`) and runs
in Node with the viewer's time zone set to UTC; its fixtures (agents, intents, messages) are in `test/fixtures/`. Hooks
and components that need a DOM get an integration tier in Vitest browser mode, like `packages/ui`, only where a unit
test of their model can't prove the behaviour.

Tests are Effect code, like the code they test:

- `it.effect` and `layer(...)` from `@effect/vitest`; `TestClock` for time; `layer(..., { excludeTestServices: true })`
  only where real time matters (and say why).
- API tests call the typed client (`HttpApiClient` against the test server, a client per user with its own cookie
  ref): typed payloads, typed successes, typed errors through `Effect.flip`. Never raw `fetch`, JSON strings, `any`,
  or hand-built requests.
- No helper functions at the top of a test file. A table of examples (`it.each`) belongs to its test; builders used by
  several files go to `fixtures/`, harness pieces to `utils/` as services or layers.

### Writing tests

Every test guards one intended behaviour: it fails on a regression of that behaviour and on nothing else.

- **Fastest level that proves it.** Pure function, then service, then API or component, then browser. A decision (a
  branch, a calculation, a parse) is a pure function with a domain name, tested directly with a table of examples;
  services, handlers and chain flows keep one test per outcome, not per case of a decision.
- **One example per test**, differing from its neighbours in one visible way that the name says. `describe` is the
  function, service or route (`describe("POST /api/trades")`, then the method); each `it` names the example
  (`"a buy over the daily budget"`, `"409: a confirm replayed"`). Reading only the names lists what is covered.
- **Input, call, output.** Write the input and the expected value out as literals in the test, call once, and compare
  the whole value (`assert.deepStrictEqual(result, expected)`), one assertion per thing checked: what came back, then
  each effect. Never derive the expected value with the code's own logic. A value the test can't know (an id, a hash,
  a time) is matched by its shape (a pattern), never by "any".
- **Cover every case** of each public function: every branch, each bound just inside, on and just outside, empty and
  full input, every failure the caller can see, repeats (the same call twice), and every setting it reads.
- **Isolated data.** Each test makes its own records (a new user, account or id) and reads back only those, so the
  suite passes shuffled, alone and in parallel. Arrange through the front door: the API's routes, the service's
  methods, the devnet's controls; never by reaching into private state. Test servers on every worker share the
  database, so none runs a schedule or watcher over everyone's rows (`SCHEDULES_ENABLED=false`): a test runs the sweep
  for its own user (`runDue(now, { userId })`, `check({ userId })`). A worker's chain is shared by the files it runs
  in turn: arrange the prices and pools a test reads (`setPrice`, `movePool`) rather than assume them.
- **No doubles of our own code.** Real implementations inside the process; at the edge, test layers and MSW (or the
  devnet for the chain). Assert state and results, not which internals were called.
- **Prune** a test that guards nothing: one that asserts removed code stays gone, what the type checker or a library
  already guarantees, a mock's own answer, private state or call order, or anything another test already proves (keep
  the faster one). Delete production code that only existed for a pruned test.
- **A bug found while testing** is not fixed in a refactor: pin today's behaviour in a test, add the right behaviour
  next to it as `it.skip("… (bug: …)")`, and report it.
- **Budgets:** about 5 ms for a pure function, 50 ms for a database or devnet round trip, 100 ms for an API request;
  one-time setup (migrations, starting the devnet) goes in `globalSetup` or `beforeAll`, never in each test.

### Chain and browser suites

Chain tests run on the devnet (`packages/devnet`): a local Base with every contract bluechip uses at its real address,
one Anvil and Alto per Vitest worker, started from a captured state file, so they need no fork, no RPC and no Docker.
Only `pnpm test:fork` (not part of `pnpm check`) reads the real chain, to check the facts the devnet copies.

The browser suite (`apps/e2e`, `pnpm test:e2e`, Playwright, not part of `pnpm check`: it takes several minutes) drives
the web app in Chromium against the real server on fixed market data and the assistant's recorded model, on its own
database (`bluechip_e2e`, recreated each run), its own devnet and its own ports (web 13000, server 18080, Anvil 18545,
Alto 14337), with a virtual WebAuthn authenticator for every Face ID step; it needs Docker's Postgres only. Run it
before pushing a change to a screen, a flow or the API the web app calls, and add a test for every new page, action or
card (coverage table in `apps/e2e/README.md`).

## Deploy

Paper and production run on Dokploy from `deploy/compose.yaml` (step by step in `deploy/README.md`), each service on
its own domain, on Postgres with pgvector:

| Service  | Image                                | Production             | Paper                        |
| -------- | ------------------------------------ | ---------------------- | ---------------------------- |
| `web`    | `apps/web/Dockerfile`: static, Caddy | `bluechip.markets`     | `paper.bluechip.markets`     |
| `server` | `apps/server/Dockerfile`: Node       | `api.bluechip.markets` | `paper-api.bluechip.markets` |

`web` is the static build behind Caddy (`VITE_*` are build args); `server` is Node running the sources in the
workspace's layout, migrations then the server, one instance only.

- **Settings.** Each deployment's are one git-ignored file, server runtime variables and web build args together, as
  Dokploy's Environment tab takes them: `deploy/.env.paper`, `deploy/.env.production`, `deploy/.env.landing`
  (`DATABASE_URL` there is a placeholder for the database's internal URL). The workstation's commands read the same
  files (`contracts deploy`, `axiom apply`, `posthog apply`, the web's `--mode paper` and production builds).
- **Origins.** Caddy (`apps/web/Caddyfile`) proxies nothing. The browser calls the server's domain (`VITE_API_URL`,
  `apps/web/src/lib/api/origin.ts`) with credentials; the server allows CORS and writes from `PUBLIC_ORIGIN` only
  (`platform/http/Cors.ts`, `OriginCheck.ts`), and Telegram's webhook goes to `API_ORIGIN`. Development, the browser
  suite and preview mode leave `VITE_API_URL` empty: the server's paths stay on the page's origin through Vite's
  proxy.
- **Images** build from the repository root (`docker build -f apps/server/Dockerfile .`); `.dockerignore` keeps env
  files, tests and local state out. A new workspace member adds its
  `package.json` line to both Dockerfiles.
- **The landing until mainnet.** `bluechip.markets` is a third deployment, the landing alone (`deploy/landing.yaml`:
  the web image with `VITE_APP_URL=https://paper.bluechip.markets`, `VITE_NETWORK=base`, paper's PostHog key, no
  `VITE_API_URL`). Links into the app go through `appHref` or `AppLink` (`apps/web/src/lib/appUrl.ts`,
  `components/AppLink.tsx`), never a hard-coded path; Caddy (`APP_URL`) and `client.tsx` send every path without a
  page of its own to the app's site; it calls no API, sends no browser telemetry, and its analytics report as paper
  money's. At mainnet, drop it and `VITE_APP_URL`.

## Repository scripts, tooling and dependencies

### Scripts

Every repository script is a command of the Effect CLI in `scripts/`: `scripts/commands/<name>.ts`, registered in
`scripts/cli.ts` and run as `node scripts/bin.ts <name>` (root `package.json` scripts call it). No JavaScript under
`scripts/`: `pnpm lint` fails on `.js`/`.mjs`/`.cjs` files there, and on imports that point the wrong way in
`apps/web/src` and `apps/server/src` (`scripts/lint/ImportDirections.ts`).

- Keep commands thin: flags and wiring in the command, logic in exported functions tested in `scripts/test/unit/` or,
  with real temporary folders (`FileSystem.makeTempDirectoryScoped`), `scripts/test/integration/`.
- Fail with the CLI's errors (`CheckFailed` for problems found, `ToolFailed` for a tool that failed); `scripts/bin.ts`
  reports them and sets the exit code. Run other tools through the `Tools` service.
- Config files (`vitest.config.ts`, `commitlint.config.ts`) are plain TypeScript: their tools load them.

### Tooling

Configuration lives at the root: `dprint.json`, `.oxlintrc.json`, `tsconfig.base.json` (compiler options and the
Effect language service), `tsconfig.packages.json` and `tsconfig.tests.json` (project references),
`vitest.config.ts`, `lefthook.yml`, `commitlint.config.ts`.

- TypeScript is TypeScript 7 (tsgo), patched with the Effect language service by `pnpm install`
  (`effect-tsgo patch`), so `pnpm typecheck` reports Effect diagnostics. Fix what they flag; silence one only when the
  flagged pattern is the point, for the next line only (`// @effect-diagnostics-next-line <rule>:off`).
- oxlint runs Effect's own rules (`@effect-kit/oxc`): import modules (`effect/Effect`), not barrels; relative imports
  end in `.ts`; `Array<T>`, not `T[]`. Never disable a rule file-wide.
- Packages export their source during development (`"./*": "./src/*.ts"`) and their build when published
  (`publishConfig.exports` → `dist`), so tests and type checks never need a build. Builds are `tsc -b` plus Babel's
  pure-call annotations, so bundlers tree-shake them like Effect.

### Dependencies

- Root and development dependencies are exact versions; published packages declare ranges (`^4.1.5`) for
  `dependencies` and `peerDependencies`. `effect` is a peer of every library.
- The pnpm catalog holds versions more than one package.json uses.
- New releases must be a day old before they install (`minimumReleaseAge`), except `effect`, `@effect/*` and
  `@effect-kit/*`. Dependency install scripts are denied unless listed in `allowBuilds`.

## Commits and pull requests

Conventional Commits with kebab-case scopes (`feat(core): add retries`); commitlint checks commits and the `PR title`
workflow checks PR titles, because PRs are squash-merged.

## Subagents

Pick a subagent's model by how hard the task is. Easy or mechanical work (moving or splitting files, renames, applying
a known pattern, formatting, simple lookups) goes to a fresh subagent on Sonnet with a complete brief: the files, the
pattern, how to verify, what to report. Use Opus subagents only for work that needs hard thinking (architecture,
tricky debugging, security review, new design). Forks run on the parent's model, so don't fork easy tasks.
